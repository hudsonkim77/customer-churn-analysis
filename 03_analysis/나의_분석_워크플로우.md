# 나의 분석 워크플로우 — 마케팅 채널 데이터 사례

Define → Acquire → Profile → Confirm → Clean → Model 6단계를, 실제로 이번에 진행한
마케팅 채널 데이터 분석(4주차 프로젝트)과 영업실적 messy 데이터 정제 두 사례에 대입해
정리한다. 가설이 아니라 실제로 실행하고 검증한 내용만 적는다.

## 1. Define — 답하고 싶었던 질문

- 캠페인 데이터(`marketing_campaigns.csv`)와 스펜드 데이터(`data_marketing_spend.csv`/BigQuery)가
  같은 채널·같은 월을 가리킬 때 서로 일치하는가? (정합성)
- 완료된 캠페인만 놓고 볼 때, 채널별로 예산 대비 실집행 비율(집행률)은 어떻게 다른가?
- 채널별로 "유입 1건당 비용"은 어떤 차이가 있는가 — 어디가 비효율적인가?

## 2. Acquire — 실제 확보 경로

두 갈래로 데이터를 확보했다.

- **로컬 CSV**: `marketing_campaigns.csv`, `data_marketing_spend.csv` (사용자가 4주차 폴더에 직접 보유)
- **BigQuery**: `hudson-bq-practice-2026.practice_dataset` — CS 5종 테이블(`data_customers` 등)이
  이미 있었고, 이번에 마케팅 3종(`data_marketing_spend`, `data_marketing_campaigns`,
  `data_sales_performance`)을 새로 적재함

별도로 **영업실적 messy 데이터**(`data_messy_영업실적.xlsx`)는 Excel 인쇄용 리포트 형태(병합 셀 +
소계 행 혼재)로, CS/마케팅과는 완전히 다른 도메인이지만 "채널별 비용"이라는 개념으로 같은
BigQuery 데이터셋에 함께 적재하기로 함(사용자 판단).

## 3. Profile — 실제로 발견한 문제

| 데이터 | 문제 | 확인 방법 |
|---|---|---|
| 마케팅 채널명 | 표기 차이 가능성(공백·전각/반각) — 실제로는 이번 데이터엔 차이 없었음 | `verify_overlap()`에서 NFKC 정규화 + 공백 제거로 방어적 처리, 대조 결과 12/12 완전 일치로 확인 |
| 영업실적(엑셀) | 병합 셀(`소속팀`), 소계 행("N팀 소계") 혼재, 텍스트로 저장된 숫자(매출액 콤마, 목표달성률 %) | `clean_영업실적.py`로 실제 정제 — forward-fill, 소계 행 분리, 텍스트→숫자 변환 |
| BigQuery 무료 티어 | DML(INSERT) 자체가 billing 미설정으로 차단됨 | `execute_sql`로 INSERT 시도 → 에러 확인, `CREATE TABLE ... AS SELECT ... FROM UNNEST(...)` (DDL)로 우회 |

## 4. Confirm — 그레인(한 행의 의미)

- `data_marketing_spend`: **채널 × 월** 1행 (예: SNS광고, 2024-06)
- `data_marketing_campaigns`: **캠페인(채널×월×차수)** 1행 — 채널×월로 집계해야 spend 그레인과 비교 가능
- `data_sales_performance`: **담당자(영업사원)** 1행, 팀 소계는 별도 테이블(`data_messy_영업실적_팀요약.csv`)로 분리해 그레인을 섞지 않음

`verify_overlap()`은 캠페인을 채널×월로 `groupby(sum)`해서 spend_df 그레인에 맞춘 뒤 대조하는
방식으로 이 문제를 해결했다.

## 5. Clean — 실제 적용한 정제 기법

| 기법 | 적용 대상 | 결과 |
|---|---|---|
| 채널명 정규화(NFKC + 공백 제거) | 캠페인 vs 스펜드 채널명 대조 | 2024-05·06월 12개 채널×월 조합 전부 일치 확인 |
| dtype 일관성(`np.nan` vs `pd.NA`) | 2024-07 캠페인 집계를 스펜드 시계열에 이어붙일 때 | `pd.NA`를 쓰면 concat 후 `impressions`/`clicks`가 object로 깨짐 → `np.nan`으로 교체해 float64 유지 |
| 병합 셀 forward-fill | 영업실적 `소속팀` | 15행(원본) → 12행(개인) + 3행(팀 요약)로 분리, 매출액 합계 검산 일치 확인 |
| 텍스트→숫자 변환 | 영업실적 매출액(콤마), 목표달성률(%) | BigQuery 적재 시 매출액은 콤마 제거 후 INT64로 변환(위키 노트의 STRING 표기와는 다른 선택 — BigQuery에서는 집계 편의를 위해 숫자형으로 저장) |

## 6. Model 이후

아직 착수 전. 지금까지는 **정합성 검증**(`verify_overlap`)과 **서술적 집계**(집행률, 유입 1건당
비용)까지만 했고, 예측이나 세그멘테이션 같은 Model 단계는 없다. 다음에 이어서 할 만한 것:

- 채널별 유입 1건당 비용 추세(시계열) 예측
- 영업실적 담당자별 목표달성률과 계약건수의 관계 회귀분석

## 7. 발표 요약 (2~3인 공유용 한 문장)

- **확보하면서 가장 판단하기 까다로웠던 것**: 실제 반출(트랙B 셋업가이드 경로)이 막혀서, 기존 스키마·값 분포·조직 구조(AG01~AG20·1~3팀)를 그대로 복제한 합성 데이터로 대체할지를 판단하는 게 가장 까다로웠다.
- **정제 규칙 중 가장 애매했던 것**: 재문의여부의 "방향성"(이 상담이 과거 재문의인지, 이후 재문의를 유발했는지)은 배경색을 True/False로 바꾼 뒤에도 여전히 불명확하게 남았다 — 기존 `data_consultations.csv`의 `is_recontact`도 같은 모호함을 갖고 있어, 정제로 해결되는 종류의 문제가 아니었다.

## 8. 이행 결과 (학습목표 5개 대조)

상담이력(2025-01·02) 사례로 아래 5개 목표를 실제로 어디까지 이행했는지 정리한다.

| # | 목표 | 이행 결과 |
|---|---|---|
| 1 | 계획대로 실제 데이터 확보 | 계획했던 실제 반출 경로(트랙B 셋업가이드)가 막혀(반출 승인 불가) 대체 경로④(공개/합성 데이터)로 전환. 기존 `data_consultations.csv`·`data_agents.csv`의 스키마·값 분포·조직 구조(AG01~AG20, 1~3팀)를 그대로 반영한 합성 데이터 `data_messy_상담이력.xlsx`(2025-01·02, 220건)로 확보 완료 |
| 2 | 진단 후 계획 대비 실제 문제 비교 | **계획(Profile 단계, 영업실적 사례 기반) 예상**: 병합 셀·소계 행·텍스트 숫자 3가지. **실제 진단**: 이 3가지 모두 나타났지만(A열 팀 병합, 팀별 소계 행 3개×2시트, 상담시간 텍스트/숫자 혼재) + 계획에 없던 유형도 추가로 발견됨 — 시트 2개로 분리, 2줄짜리 그룹 헤더("상담 결과"→처리결과/재문의여부), 상담일 3가지 형식(표준/점표기/엑셀 일련번호) 혼재, 재문의여부가 텍스트가 아니라 **배경색으로만** 인코딩. 즉 영업실적 사례의 문제 유형을 그대로 일반화할 수 없었다 |
| 3 | 정제 규칙 문서화 + 재실행 스크립트 | `정제_규칙_상담이력.md`(5개 규칙, 무엇/왜/검증 포함)로 문서화, `my-wiki-02/02_data/clean_상담이력.py`로 스크립트화. 동일 입력 2회 연속 실행 → 출력 CSV 2종 MD5 완전 일치로 멱등성 검증 |
| 4 | 기존 시스템 데이터와 대조 검증 | 채널·문의유형·처리결과 값 집합이 `data_consultations.csv`와 정확히 일치 확인 → BigQuery `data_consultations`에 2025-01·02월분 220건 추가 적재(1,320→**1,540행**, 기존 행 보존 확인) → `my-wiki-02/app.py`·`customer-churn-dashboard-web` 양쪽 차트 재계산까지 검증(②번 CSAT는 불변, 재문의율·③번은 갱신됨을 직접 확인) |
| 5 | 표본 크기 근거로 지표 신뢰 판단 | 채널·문의유형별 재문의율 계산(전 구간 표본 126건 이상, 30건 미만 규정에는 안 걸림). 다만 **신규 220건만 따로 보면 앱 채널이 27건(30건 미만)**으로 참고용 판정 — 이 좁은 표본만으로는 14.8%가 나오지만, 누적 전체(143건) 기준으로는 23.8%로 실제 결론이 달라짐을 직접 확인해 표본 크기 경고를 실전 적용함 |

## 9. 정제 결과 애로점 (최종 정리)

정제 규칙을 다 적용하고 검증까지 마친 뒤에도, 코드로 해결되지 않고 남은 애로점:

- **재문의여부의 방향성 모호함**: 배경색→True/False 변환은 "표시 방식"의 문제를 풀었을 뿐, "이 상담이 과거 재문의인지 vs 이후 재문의를 유발했는지"라는 의미 자체의 모호함은 그대로 남았다. 기존 `data_consultations.csv`의 `is_recontact`도 동일한 모호함을 갖고 있어, 이번 정제로 새로 생긴 문제가 아니라 원본 스키마 설계 단계부터의 한계였다.
- **상담일의 의미 불확실**: 접수일/진행일/완료일 중 무엇을 가리키는지 정제 후에도 확정할 수 없었다 — 형식은 통일했지만 "의미"는 통일 대상이 아니었다.
- **행 고유 식별자 부재**: `consult_id` 같은 PK가 없어, 완전히 동일한 값 조합의 행이 나와도 "중복 오류"인지 "우연히 같은 값의 별개 상담"인지 정제 로직만으로는 구분할 수 없었다(BigQuery 적재 시 별도로 순번을 채번해 해결한 것이지, 원본 데이터의 모호함이 사라진 것은 아니다).
- **도구적 어려움**: 재문의여부가 텍스트가 아니라 배경색으로만 인코딩돼 있어, `pandas.read_excel`처럼 값만 읽는 방식으로는 이 정보 자체가 보이지 않았다 — `openpyxl`로 셀의 `fill.fgColor`까지 직접 열어봐야 했고, 이는 "값이 비어있다"와 "값이 색으로 표시돼 있다"를 구분하는 별도 진단 없이는 놓치기 쉬운 문제였다.
